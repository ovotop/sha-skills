# 中文受控写作规则（全表）

本文件是中文受控写作规则的**权威源**（skill 运行时实际读取）。`docs/rules.md` 是面向读者的**展示副本**，内容允许滞后，修订以本文件为准。

从 ASD-STE100 到中文的“受控写作”，核心思路不是翻译规则，而是**移植其“降低歧义”的方法论**。以下是可借鉴的核心思路与具体规则。

---

### 🧭 可借鉴的核心思路

ASD-STE100 的本质是一套**写作约束器**，而非知识生成器。它的目标是让输出更小心、可执行、无歧义。中文受控写作可以从以下几个层面借鉴：

**1. 从“作者友好”转向“读者友好”**
ASD-STE100 为母语非英语的读者设计，强制作者放弃个人风格，服从统一的表达规范。中文受控写作同样应优先考虑读者能否**一次读懂、准确执行**。

**2. 区分“事实”与“修辞”**
受控语言的核心是**保留事实，削减修辞**。不新增原文没有的数字、日期、条件或结论，不删除警告、限制和例外，不把“可能”改成“一定”。

**3. 用规则替代直觉**
“说人话”是主观判断，“一句不超过 40 字”是可执行约束。ASD-STE100 有 53 条写作规则和约 900 个核准词。中文受控写作也需要把模糊的“清晰”转化为可操作的量化标准。

**4. 区分适用强度**
受控规则不应一刀切。操作手册、故障排查、安全警告适合**完整应用**；API 概念说明、更新日志适合**选择性应用**（术语一致、指代明确）；品牌文案、叙事性文章则**不机械应用**。


### 📐 具体规则清单

#### 一、词汇层面

| 规则 | 具体做法 | 来源依据 |
| :--- | :--- | :--- |
| **一词一义** | 为关键对象、状态和动作确定**首选术语**，不因怕重复而轮换同义词 |  |
| **缩写规范** | 首次出现给出全称，后文保持同一写法 |  |
| **消除多义词歧义** | 同一个词存在多个含义时，用更具体的词替代，而非机械替换 |  |
| **避免模糊副词** | 禁用“非常”“特别”“基本上”等无法量化的修饰词 | ASD-STE100 核心原则 |
| **避免黑话与冗余** | 避免“赋能”“抓手”“闭环”等互联网黑话；避免机械直译 `Success`、`Invalid` 等英文状态词 |  |
| **明确指代** | 不使用“该”“其”“此”“上述”“相关”等无法定位对象的词 |  |

#### 二、句子层面

| 规则 | 具体标准 | 来源依据 |
| :--- | :--- | :--- |
| **句长限制** | 不使用逗号时不超过 **40 字**；以逗号分隔的构件尽量保持在 **20 字以内**；30–39 字的句子语义必须明确才可接受；**超过 40 字在任何情况下都不能接受** | 阮一峰《中文技术文档写作规范》 |
| **一句一义** | 一个句子只保留一个清晰的主干，不连续堆叠多个条件、动作和例外 |  |
| **显式主语** | 每个句子都应有明确的主语，避免无主句导致责任或指代歧义 | 受控中文研究 |
| **主动语态优先** | 使用主动语态，明确执行者；区分系统自动行为和人工操作 |  |
| **逻辑关系完整** | 句子结构完整，句内和句间逻辑关系清晰，不省略必要的条件、否定和因果 | 受控中文研究 |
| **否定范围明确** | 禁止的是哪个动作必须清晰，避免读者无法判断 |  |

#### 三、结构与顺序

| 规则 | 具体做法 | 来源依据 |
| :--- | :--- | :--- |
| **一步一动作** | 步骤以明确动作开始；写清动作对象，不只写“处理”“操作”“执行”；多个顺序动作拆成编号步骤 |  |
| **条件与风险先行** | 执行动作前必须知道的条件放在动作之前；警告放在可能造成风险的步骤之前；不把关键限制放在步骤末尾的括号中 |  |
| **逻辑顺序** | 按实际执行顺序排列；故障排查先给低风险、可逆、证据价值高的检查 |  |
| **原因、现象、操作、结果分离** | 不混在一个长句中 |  |
| **一段一信息点** | 一个段落承载一个主要信息点 |  |

#### 四、标点与格式

| 规则 | 具体做法 | 来源依据 |
| :--- | :--- | :--- |
| **标点一致** | 全角标点，中文与英文数字之间加空格 |  |
| **列表项对齐** | 同一列表中各条目保持相同层级、句式和信息密度 |  |
| **标题反映用途** | 不只使用抽象名词 |  |

#### 五、模板化结构（操作与排查场景）

**操作步骤模板**：
1. 前置条件
2. 风险或限制
3. 编号操作步骤
4. 每一步的预期结果
5. 失败时的停止条件和恢复方式

**故障排查模板**：
1. 可观察到的现象
2. 需要收集的日志、状态或错误码
3. 按证据和风险安排检查顺序
4. 每项检查的判断条件
5. 只有证据支持时才给出原因
6. 恢复操作、验证方式和停止条件


### 💎 总结

这些规则的可迁移内核可以概括为三条：**保留事实**（不增删关键信息）、**一词一义**（消除词汇歧义）、**一步一动作**（消除结构歧义）。ASD-STE100 的英文词典和时态规则无法直接移植到中文，但“用可执行约束替代主观判断”的方法论，以及上述基于中文句法重新表述的具体规则，已经足以构成一套可用的中文受控写作框架。

### 混排与标点细则（可机械检查）

- 正文用全角标点（，。；：？！（））；代码、路径、命令、变量名保持原样。
- 中文与英文单词、数字之间加一个半角空格：`配置 maxConnections 为 200`。
- 数字与全角标点之间不加空格：`超时 30 秒。`
- 单位与数字之间加空格，`%` 与前一个数字之间不加：`占用 30%`。

### SCQA 变体 → 文档类型映射

- 操作手册：背景=读者要完成某任务，冲突=现有做法易出错，问题=如何安全完成，答案=本手册的编号步骤。
- API 说明：背景=读者要接入某能力，冲突=接口约束多，问题=参数与返回如何配对，答案=按场景给出示例。
- 更新日志：背景=读者已在用旧版本，冲突=行为有变，问题=哪些调用会受影响，答案=按影响面分级列出变更。
- 故障排查：背景=读者面对某现象，冲突=原因不唯一，问题=先查什么，答案=按证据强度排序的检查清单。

序言只写背景与冲突（读者已知的部分）；答案进正文，避免序言变成摘要。
